# Event Processor

Сервис принимает события кликов и покупок, связывает их по `clid` и отправляет объединённые данные в AdVantage.

Для реализации я использовала Python, FastAPI и PostgreSQL. Отправка работает в отдельном процессе — worker. API сохраняет события в БД и подтверждает приём, не дожидаясь ответа AdVantage.

## Запуск

Нужен Docker с Docker Compose.

Скопируйте `.env.example` в `.env` и задайте свой `POSTGRES_PASSWORD`.

В PowerShell:

```powershell
Copy-Item .env.example .env
```

Если `.env` уже существует, перезаписывать его не нужно.

Запустите проект:

```bash
docker compose up -d --build
```

Compose поднимает четыре сервиса:

- `db` — PostgreSQL;
- `api` — приём событий;
- `worker` — доставка;
- `mock-advantage` — локальный получатель для проверки.

После запуска доступны:

- [Документация API](http://127.0.0.1:8000/docs)
- [Проверка работы API](http://127.0.0.1:8000/health)
- [Документация тестового получателя](http://127.0.0.1:8001/docs)

PostgreSQL доступна с компьютера на `127.0.0.1:15432`.

В демонстрационной конфигурации worker отправляет запросы в `mock-advantage`. Адрес из задания не используется, поскольку по ТЗ он не работает.

## Приём событий

### Клик

`POST /events/clicks`

```json
{
  "clid": "example-1",
  "ad_id": 17,
  "click_spend": 1.25,
  "ts": "2026-09-13T13:00:00+03:00"
}
```

### Покупка

`POST /events/payments`

```json
{
  "clid": "example-1",
  "payout": 30.00,
  "ts": "2026-09-13T13:05:00+03:00"
}
```

При успешном сохранении API возвращает `202`:

```json
{
  "clid": "example-1",
  "inserted": true
}
```

Для повторного события возвращается тот же статус с `inserted: false`.

Ответ `202` означает, что событие сохранено или распознано как повтор. Он не означает, что данные уже доставлены в AdVantage.

При ошибке валидации возвращается `422`. Необработанная внутренняя ошибка может привести к `500`. Предполагается, что источники повторяют запросы, если не получили подтверждение приёма.

## Как устроена обработка


Клики хранятся в таблице `clicks`, покупки — в `payments`. В записи покупки также находятся состояние доставки, число попыток, последняя ошибка и данные захвата задачи.

Правила уникальности заданы на уровне PostgreSQL:

- для клика — `clid`;
- для покупки — пара `(clid, ts)`.

Поэтому у одного клика может быть несколько покупок с разным временем. Каждая отправляется отдельно.

Повторные события не меняют сохранённую запись. Если у повторного клика отличаются данные или у повторной покупки изменилась сумма, сервис пишет предупреждение в лог.

Покупка может прийти раньше клика. В этом случае она сохраняется в БД, но worker не выбирает её для отправки. Когда клик появляется, данные становятся доступны для объединения без повторного запроса от Payment Service.

## Доставка и повторы

Worker выбирает покупку, если:

- для неё уже есть клик;
- доставка ещё не подтверждена;
- наступило время следующей попытки;
- задача не занята другим worker или срок захвата истёк.

Для захвата используется короткая транзакция с `FOR UPDATE SKIP LOCKED`. Worker записывает срок захвата и новый `claim_token`, после чего завершает транзакцию.

HTTP-запрос выполняется без удержания соединения с БД.

После ответа `200` worker заполняет `delivered_at` и освобождает захват. Любой другой статус или сетевая ошибка приводит к назначению повтора. Задержка увеличивается со случайным разбросом до 300 секунд. Ограничения на количество попыток нет.

Результат записывается только при совпадении токена захвата. Если задачу уже забрал другой worker, старый процесс не сможет перезаписать её состояние.

Если worker остановился до завершения обработки, задача снова станет доступна после истечения срока захвата.

Доставка работает по принципу at least once: повторные отправки возможны. Например, AdVantage мог принять запрос, но ответ потерялся или worker не смог сохранить результат в БД. По условиям задания дедупликацию на стороне получателя выполняет сам AdVantage.

## Принятые допущения

В ТЗ не указан источник валют, хотя они обязательны в исходящем сообщении. Поэтому я вынесла их в настройки `PAYOUT_CURRENCY` и `CLICK_SPEND_CURRENCY`. Предполагается, что каждый источник передаёт суммы в одной настроенной валюте. Конвертация валют не выполняется.

Время принимается только с часовым поясом. В примерах используется московское время, в БД — `TIMESTAMPTZ`. Разные записи одного момента, например `13:00+03:00` и `10:00Z`, не создают разные покупки.

Для сумм используются `Decimal` в Python и `NUMERIC` в PostgreSQL. При формировании JSON десятичные значения сериализуются без преобразования в `float`.

Отрицательные суммы не запрещены: в задании не определено, могут ли источники передавать возвраты или корректировки.

Если совпадают ключи события, сохраняется первая принятая версия. Две реальные покупки с одинаковыми `clid` и `ts` невозможно различить без дополнительного идентификатора покупки.

Автоматическое удаление событий не реализовано, поскольку максимальная задержка между кликом и покупкой не задана.

## Тесты

Запуск автоматических тестов внутри контейнера:

```bash
docker compose exec api python -m unittest -v test_schemas test_delivery test_repository
```

Набор содержит 18 тестов. Проверяются:

- валидация событий;
- сохранение точности сумм в JSON;
- обработка HTTP-статусов и тайм-аутов;
- дубли и конфликтующие данные;
- покупка, поступившая раньше клика;
- выбор разных задач двумя соединениями;
- истечение захвата и защита от устаревшего токена;
- сохранение состояния повторной попытки.

Тесты PostgreSQL создают отдельные схемы и удаляют их после выполнения. Рабочие таблицы не используются для тестовых вставок.

Проверка полного сценария через API и worker:

```bash
docker compose exec api python check_e2e.py
```

Скрипт отправляет покупку до клика, проверяет ожидание, добавляет клик и дожидается доставки. Затем повторяет покупку и проверяет, что новая запись не появилась, а отметка доставки сохранилась.

После проверки в БД остаются события с уникальным идентификатором `e2e-...`.

Локальный получатель проверяет структуру сообщения и возвращает `200`. Это вспомогательный сервис: он не реализует хранение, дедупликацию и проверку токена как полноценный AdVantage.

## Настройки

Основные параметры находятся в `.env.example`.

| Переменная | Назначение |
|---|---|
| `POSTGRES_HOST`, `POSTGRES_PORT` | Адрес PostgreSQL |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Данные подключения |
| `DB_POOL_MIN_SIZE`, `DB_POOL_MAX_SIZE` | Размер пула одного процесса |
| `WORKER_POLL_INTERVAL` | Пауза при отсутствии доступных задач |
| `WORKER_LEASE_SECONDS` | Срок захвата задачи |
| `ADVANTAGE_URL` | Адрес получателя |
| `ADVANTAGE_TOKEN` | Токен авторизации |
| `ADVANTAGE_HTTP_TIMEOUT` | Сетевой тайм-аут HTTPX |
| `PAYOUT_CURRENCY` | Валюта покупок |
| `CLICK_SPEND_CURRENCY` | Валюта стоимости кликов |

Compose переопределяет адрес PostgreSQL на `db:5432`, а адрес получателя для worker — на локальный сервис `mock-advantage`.

Полная длительность отправки дополнительно ограничена в коде worker 20 секундами.

`.env` не должен попадать в репозиторий.

## Миграции

Миграции находятся в `migrations/` и выполняются через `migrate.py`.

При запуске Compose отдельный сервис `migrate` применяет изменения
до запуска API и worker. Завершение этого контейнера с кодом 0
означает успешное выполнение.

В таблице `schema_migrations` сохраняются имя файла, контрольная
сумма и время применения. Повторный запуск пропускает применённые
миграции. Если изменить уже применённый файл, мигратор сообщит
об ошибке. Для изменения схемы нужно добавить новую миграцию.

Мигратор использует блокировку PostgreSQL, чтобы два запуска
не применяли изменения одновременно. Каждая миграция выполняется
в отдельной транзакции.

Ручной запуск:

```bash
docker compose run --rm migrate
```

Первая миграция совместима с ранее созданными таблицами этого
проекта. При этом `IF NOT EXISTS` не проверяет соответствие
произвольной существующей таблицы ожидаемой структуре.

Миграции выполняются только вперёд. Автоматический откат версий
и нетранзакционные миграции пока не реализованы.

`schema.sql` используется для создания таблиц в изолированных
интеграционных тестах. При изменении структуры его нужно
обновлять вместе с добавлением новой миграции.

Проверена установка на пустой БД через отдельный Compose-проект:
обе миграции применяются, создаются таблицы `clicks`, `payments`
и `schema_migrations`. Повторное применение миграций не меняет схему.

Конфигурация этой проверки находится в `compose.fresh.yaml`.

## Нагрузочная проверка

Проверка выполнялась локально: генератор на Windows 11,
Python 3.12.10, приложение и PostgreSQL в Docker Desktop.
Использовались один процесс API, один worker и локальный
тестовый AdVantage. Максимум соединений в каждом пуле — 5.

Генератор ограничивает число одновременно выполняемых запросов,
а не поддерживает фиксированную скорость отправки.
Неуспешные запросы он не повторяет.

| Показатель | Короткий прогон | Основной прогон |
|---|---:|---:|
| Всего событий: клики и покупки | 200 | 4 000 |
| Одновременные отправители | 10 | 25 |
| Время приёма, с | 0,443 | 13,048 |
| Успешно принято событий/с | 451,38 | 306,56 |
| p95 ответа API, мс | 51,52 | 263,75 |
| Ошибки приёма | 0 | 0 |
| Доставлено покупок | 100 из 100 | 2 000 из 2 000 |
| Всего попыток доставки | 100 | 2 000 |
| Покупок в очереди после приёма | 100 | 287 |
| Дополнительное ожидание доставки, с | 2,017 | 2,018 |

В основном прогоне все события были приняты, а очередь полностью
обработалась после завершения входящего потока.

Для повторения проверки нужен Python 3.12 и локальное окружение
с установленными зависимостями:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Если окружение уже подготовлено, достаточно активировать его.
Docker Compose должен быть запущен, а настройки подключения
в `.env` должны указывать на опубликованный порт PostgreSQL:
`127.0.0.1:15432`.

Команда основного прогона:

```powershell
python load_test.py --pairs 2000 --concurrency 25 --drain-timeout 300 --output load-results/c25.json
```

Результаты сохраняются в JSON. Тестовые события остаются в БД
с уникальным префиксом `load-`.

Эти результаты относятся к конкретному локальному запуску.
Они не определяют максимальную пропускную способность сервиса.
Прогоны отличаются объёмом и длительностью, поэтому по ним
нельзя отдельно оценить влияние увеличения параллелизма.

Тестовый AdVantage отвечает быстро. Задержки реального получателя
могут существенно повлиять на скорость доставки.

Состояние очереди проверяется раз в секунду, поэтому измерение
времени окончания доставки имеет соответствующую погрешность.
Длительная перегрузка и работа на больших объёмах истории
этими прогонами не проверялись.

## Ограничения и дальнейшие улучшения

Worker обрабатывает одну покупку за раз. Механизм захвата
позволяет использовать несколько worker; конкурентный выбор
проверен на двух соединениях с БД. Нагрузочный тест нескольких
процессов worker пока не проводился.

`/health` проверяет ответ приложения, но не является полной
проверкой доступности его зависимостей.

Для дальнейшей доработки я бы добавила:

- отдельную роль PostgreSQL с минимальными правами;
- метрики очереди и оповещения о длительных ошибках;
- централизованную конфигурацию;
- полную фиксацию транзитивных зависимостей;
- автоматические проверки миграций;
- тесты аварийного завершения процессов и длительной нагрузки.

Окончательная доставка зависит от сохранности БД, поступления
соответствующего клика и восстановления работы получателя.
Если токен или формат запроса некорректны, повторные попытки
сохраняют задачу, но причину ошибки нужно исправить.
